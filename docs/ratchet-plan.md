# План: Double Ratchet для DNS Messenger

Статус: **фазы 1–4 реализованы и покрыты тестами** (`ratchet.py`,
`crypto_utils.py`, `tests/test_ratchet.py`, `tests/test_dm_ratchet.py`,
`tests/test_ratchet_persistence.py`, `tests/test_prekey_rotation.py`,
`tests/test_safety_number.py`, `tests/test_group_rekey.py`, интеграция в
`web_client.py`/`server.py`). Рестарт сервера (у вас частые деплои — см.
`deploy.sh`) больше не рвёт активные переписки.

## Почему это вообще нужно

Сейчас (`crypto_utils.py`, `Identity.derive_shared_key`) общий ключ между
двумя людьми — это статический `ECDH(A.private_key, B.private_key)`,
пересчитываемый заново на каждое сообщение из ОДНОЙ И ТОЙ ЖЕ пары X25519-ключей
на весь срок жизни аккаунта (`web_client.py`, вызовы `derive_shared_key()` на
строках ~737, 879, 931, 964, 995).

Последствие: тот, кто записывает DNS-трафик сейчас (шифротекст, без
содержимого), а когда-либо в будущем получает identity-ключ жертвы (кража
пароля, компрометация сервера — см. обсуждение модели доверия в этой же
переписке), расшифровывает **всю** историю переписки этого человека задним
числом. Ни forward secrecy, ни post-compromise security сейчас нет.

Групповые чаты (`generate_group_key`/`seal_group_key`/`unseal_group_key`)
устроены даже проще — один статический симметричный ключ на группу, без
ре-кея вообще; функций «выйти из группы»/«кикнуть участника» в коде нет.

## Согласованные решения (из грилинг-сессии)

| # | Вопрос | Решение |
|---|---|---|
| 1 | Глубина фикса | Полный Double Ratchet (не упрощённый ephemeral-per-session) |
| 2 | Начальный handshake при офлайн-получателе | X3DH-подобные prekey bundles (identity + signed prekey + one-time prekeys) |
| 3 | Группы | Sender Keys (Signal-style), заодно решает отсутствие кика/leave |
| 4 | Rollout | Жёсткое переключение, без версионирования протокола (весь код — один деплой) |
| 5 | Лимит пропущенных ключей | Есть, порядка 500–1000 на сессию (тот же порядок, что текущий `msg_buffer` cap = 500) |
| 6 | Персистентность ratchet-состояния | Да, зашифровано паролем аккаунта — деплои перезапускают сервис часто, разрыв всех сессий на каждый деплой неприемлем |
| 7 | Safety number | Да, но **опционально** (не блокирует отправку) — доступно из профиля контакта |
| 8 | Формат safety number | Числовой код (как Signal) + QR |

## Явно вне рамок этого плана

Отдельно обсуждались и **сознательно не включены** сюда:
- **Traffic analysis / метаданные** — принято как ограничение DNS-туннеля,
  адаптивный поллинг (`next_poll_delay`) уже частичная защита, полное решение
  (padding, constant-rate) — отдельная большая тема, не часть ratchet-работы.
- **Admin break-glass** — уже реализовано отдельно (`purge_username_data()`),
  не относится к ratchet.

## Фаза 1 — X3DH + парный Double Ratchet (личные чаты) — РЕАЛИЗОВАНО

Ядро работы. Группы на этом этапе остаются на старой статической схеме —
намеренно, чтобы не смешивать протокольную смену с групповой логикой.

**Отклонение от исходного эскиза, обнаруженное при реализации:** в плане
ниже изначально предполагался отдельный `POST /api/prekeys/publish`. От него
отказались — пароль аккаунта нигде не хранится дольше момента логина (см.
`Identity.load`/`UserMessenger.__init__`), а значит re-encrypt `prekeys.key`
физически возможен ТОЛЬКО там, где пароль ещё жив, то есть в момент
конструирования `UserMessenger`. Публикация и пополнение пула теперь —
часть `UserMessenger.__init__` (`bootstrap_or_replenish_prekeys` +
`publish_prekey_bundle`), происходит автоматически при каждом логине.
Аналогично отпал и `GET /api/prekeys/bundle/<username>` как HTTP-эндпоинт:
обмен бандлами — внутренняя серверная бухгалтерия между `send_dm`/
`_decrypt_from` и `PREKEY_FILE` в рамках одного процесса, браузеру тут
вообще нечего вызывать напрямую (`take_prekey_bundle()` — обычный Python-
вызов, не сетевой запрос).

**Реализовано:**
- `ratchet.py` — X3DH (`x3dh_initiate`/`x3dh_respond`) + `RatchetSession`
  (полный Double Ratchet: DH-ratchet шаги, KDF-цепочки, лимит пропущенных
  ключей `MAX_SKIPPED_KEYS`, заголовок аутентифицирован как AAD).
- `crypto_utils.encrypt`/`decrypt` — расширены опциональным `aad` (обратно
  совместимо, по умолчанию `None`, ни один существующий вызов не изменился).
- `web_client.py`: `PREKEY_FILE` (публичные бандлы), `.messenger_<user>/prekeys.key`
  (приватные половины, зашифрованы паролем аккаунта той же схемой, что
  identity.key), `bootstrap_or_replenish_prekeys`/`publish_prekey_bundle`/
  `take_prekey_bundle`, интеграция в `UserMessenger.__init__`/`send_dm`/
  `_decrypt_from` с трёхсхемным wire-форматом
  (`RATCHET_SCHEME_LEGACY_STATIC`/`_INIT`/`_CONT`) — легаси-путь остаётся
  для анонимного режима (без persistent identity ratchet бессмысленен) и как
  автоматический фолбэк, если у получателя ещё нет опубликованного бандла.
- **Ротация signed prekey** (`SIGNED_PREKEY_ROTATE_AFTER` = 7 дней) —
  добавлена уже ПОСЛЕ первого прохода, когда обнаружилось, что исходная
  реализация генерировала signed prekey один раз и никогда не обновляла его.
  Известная граница: X3DH-хендшейк, начатый непосредственно перед ротацией
  получателя, но долетевший уже после неё, безопасно провалится (сообщение
  придётся отправить заново) — предыдущий signed prekey «ещё валидным» на
  переходный период сознательно не держим, недели между ротациями против
  секунд доставки через DNS-туннель делают это исчезающе маловероятным.
- `tests/test_ratchet.py` — корректность примитивов (roundtrip, out-of-order,
  forward secrecy, лимит пропущенных ключей, отказ на подделанной подписи
  prekey).
- `tests/test_dm_ratchet.py` — интеграционный тест через реальный
  `RelayServer`+`UserMessenger` (по образцу `test_group_auth.py`):
  X3DH-хендшейк потребляет ровно один one-time prekey, переписка продолжается
  на ratchet-continue, аноним корректно остаётся на легаси-схеме без побочных
  эффектов на чужие ratchet-сессии, рестарт `UserMessenger` корректно рвёт
  сессию с явной ошибкой вместо краша/тихой порчи данных.
- `tests/test_prekey_rotation.py` — bootstrap с нуля, пополнение просевшего
  пула, ротация просроченного signed prekey, подпись нового prekey всё ещё
  проверяется под тем же identity-ключом.

### Криптопримитивы (`ratchet.py`) — как построено по факту

- **Signed prekey**: X25519-пара, подписанная Ed25519 identity-ключом
  (`sign_prekey`), ротируется каждые `SIGNED_PREKEY_ROTATE_AFTER` (7 дней) —
  проверка идёт в `bootstrap_or_replenish_prekeys`, то есть привязана к
  логину, а не к таймеру процесса (в отличие от clock-driven подхода из
  референса ниже). Предыдущее поколение сознательно не хранится валидным —
  см. заметку про известную границу в «Реализовано» выше. Покрыто
  `tests/test_prekey_rotation.py`.
- **One-time prekeys**: пул X25519-пар (`ONE_TIME_PREKEY_POOL_TARGET = 50`),
  пополняется в `UserMessenger.__init__` при каждом логине, если просел ниже
  `ONE_TIME_PREKEY_REPLENISH_THRESHOLD = 10`. Каждый выдаётся ровно одному
  запросившему (`take_prekey_bundle`, атомарно под `prekey_lock`) и
  безвозвратно удаляется из публичного пула в момент выдачи.
- **X3DH-вывод общего секрета** (`x3dh_initiate`/`x3dh_respond`): комбинация
  DH между `(identity_A, signed_prekey_B)`, `(ephemeral_A, identity_B)`,
  `(ephemeral_A, signed_prekey_B)`, и, если one-time prekey был доступен,
  `(ephemeral_A, one_time_prekey_B)` — через HKDF в один root key. Если
  one-time prekeys закончились, используется вариант без последней
  компоненты (чуть слабее, но не блокирует переписку — как у Signal).
  Проверено тестом `test_x3dh_without_one_time` в `test_ratchet.py`.
- **Double Ratchet** (`RatchetSession`): root chain (обновляется на каждый
  DH-ratchet шаг при смене направления переписки) + send/receive chain keys
  (HMAC-цепочка на каждое сообщение внутри одного направления). Заголовок
  (`dh_pub || pn || n`) передаётся в открытом виде (без header encryption —
  см. док-строку модуля), но аутентифицирован как AAD.

### Формат хранения на сервере — как построено по факту

- `PREKEY_FILE` (`.messenger_prekeys.json`, plaintext JSON, как
  `.messenger_webauthn.json`): username → {signed_pub, signed_sig, signed_ts,
  one_time: [публичные ключи]}. Публичная часть — не секрет.
- Приватные половины — `.messenger_<user>/prekeys.key`, зашифрованы паролем
  аккаунта той же схемой (scrypt + ChaCha20-Poly1305), что `identity.key`
  (`_derive_identity_key`, переиспользован формат, не изобретён новый).
- Ratchet-состояние — `.messenger_<user>/ratchet_<peer>.state`, один файл на
  пару собеседников, зашифрован ключом из `ratchet_storage_key()` (выведен из
  уже расшифрованной identity, а не из пароля напрямую — пароль нигде не
  хранится дольше момента логина). Загружается целиком в
  `UserMessenger.__init__`, дозаписывается после каждого `encrypt`/`decrypt` —
  рестарт сервера (частые деплои, см. `deploy.sh`) больше не рвёт активные
  переписки. Реализовано в фазе 2, покрыто `tests/test_ratchet_persistence.py`
  и restart-сценарием в `tests/test_dm_ratchet.py`.

### Эндпоинтов не появилось — публикация/обмен бандлами локальны серверу

От `POST /api/prekeys/publish` и `GET /api/prekeys/bundle/<username>` из
исходного эскиза отказались при реализации — см. врезку «Отклонение от
исходного эскиза» выше.

### Лимит на пропущенные ключи

Как решили — порог ~500–1000 пропущенных ключей на сессию (пара
собеседников). При превышении: отбрасываем самые старые пропущенные ключи
цепочки (сообщение, которое придёт совсем поздно, станет нечитаемым — крайний
случай, не типичный сценарий при обычной доставке).

### Тесты (обязательно, по конвенции проекта — файл на фичу)

`tests/test_ratchet.py`, по образцу `test_crypto_auth.py`/`test_identity_enc.py`:
- roundtrip: A шифрует, B расшифровывает, при обычном порядке сообщений;
- сообщения не по порядку (B получает №3 раньше №2) — оба расшифровываются;
- потерянное сообщение не блокирует остальные;
- ключ каждого сообщения уникален (снимок chain key до/после не совпадает);
- компрометация текущего chain key НЕ вскрывает уже отправленные ранее
  сообщения (это и есть forward secrecy — тест должен явно это проверять,
  а не просто гонять roundtrip);
- X3DH: получатель офлайн в момент отправки, prekey bundle используется
  ровно один раз, one-time prekey не переиспользуется;
- исчерпание one-time prekeys — handshake всё равно проходит (без
  one-time-компоненты), просто это отдельно помечается в тесте;
- лимит пропущенных ключей — превышение обрабатывается предсказуемо
  (без падения процесса, без неограниченного роста памяти — тест по
  аналогии с `test_relay_dos.py`).

## Фаза 2 — Персистентность ratchet-состояния — РЕАЛИЗОВАНО

**Отклонение от исходного эскиза:** ключ шифрования `ratchet_<peer>.state`
выводится НЕ из пароля напрямую (`_derive_identity_key`, как предполагалось
изначально), а из уже расшифрованной `Identity` через HKDF
(`ratchet_storage_key` в `ratchet.py`). Причина та же, что и в фазе 1: пароль
нигде не хранится дольше момента логина, а состояние ratchet дозаписывается
на диск после КАЖДОГО сообщения (не только при логине, в отличие от
prekeys.key) — если бы ключ шифрования требовал пароль, переписывать файл
можно было бы только в `__init__`, а не после каждого `encrypt`/`decrypt`.
Уровень защиты тот же: кто способен расшифровать `identity.key` паролем,
способен вычислить и этот ключ.

**Реализовано:**
- `RatchetSession.to_dict()`/`from_dict()` в `ratchet.py` — полная
  сериализация состояния (root key, обе DH-пары, обе цепочки, счётчики,
  таблица пропущенных ключей).
- `web_client.py`: `save_ratchet_state`/`load_ratchet_state`/
  `load_all_ratchet_states`, файл на пару собеседников —
  `.messenger_<user>/ratchet_<peer>.state`, права 600, тот же `os.open`-
  паттерн, что у `identity.key`.
- Загрузка всех существующих сессий — в `UserMessenger.__init__`, сразу
  после prekeys.
- Запись — после КАЖДОГO `encrypt`/`decrypt` (`UserMessenger._persist_ratchet`),
  и в `send_dm`, и в `_decrypt_from`, в обеих ratchet-ветках каждого метода —
  не батчем, чтобы не было окна между реальным состоянием переписки и тем,
  что на диске.
- **Побочный баг, найденный и исправленный по ходу**: в ветке
  `RATCHET_SCHEME_RATCHET_CONT` в `_decrypt_from` открытие подписанного
  сообщения (`open_signed`) требует Ed25519 verify-ключ пира из
  `self.peer_verify` — а тот, в отличие от самого ratchet-состояния, НЕ
  персистентен и живёт только в памяти объекта. На свежевосстановленном
  после рестарта объекте он пуст, и первое же входящее ratchet-сообщение
  показывалось бы как `unverified` вместо `verified`, хотя криптографически
  расшифровывалось верно. Пойман интеграционным тестом
  `test_dm_ratchet.py` (не unit-тестом на примитивы — ещё один аргумент
  держать сквозной интеграционный тест, не только на изолированные функции).
  Исправлено явным вызовом `self.peer_verify_key(sender)` в начале этой ветки.
- `tests/test_ratchet_persistence.py` — сохранение/восстановление с верным и
  неверным ключом, битый файл, несколько пиров одновременно, сырые секреты
  не попадают на диск.
- `tests/test_dm_ratchet.py` дополнен: «рестарт» `UserMessenger` (тот же
  пароль, тот же диск) теперь прозрачно восстанавливает сессию — bob
  продолжает переписку с alice без нового X3DH, сообщение расшифровывается
  и проверяется корректно.

## Фаза 3 — Safety number — РЕАЛИЗОВАНО

Ручная сверка identity-ключей вне канала (реш. #7/#8): опциональна, не
блокирует отправку — TOFU-пиннинг (`_remember_peer`/`key_alerts`) и так уже
ловит подмену бандла на лету, этот экран нужен только для сверки при первом
контакте, до того как есть с чем сравнивать пин.

**Отклонение от исходного эскиза:** формат — числовой код (как и решили),
QR не реализован в этом проходе (потребовал бы либо новую pip-зависимость на
сервере, либо вендоренную JS-библиотеку в клиенте — сознательно отложено как
отдельная единица работы, а не забыто).

**Реализовано:**
- `crypto_utils.py`: `identity_fingerprint()` (итерированный SHA-512,
  `SAFETY_NUMBER_ROUNDS = 5200` — тот же порядок, что у Signal, дороже
  подобрать коллизию, чем одиночным хешем), `safety_number()` (60-значный
  комбинированный отпечаток пары, симметричный — сортировка по имени
  пользователя, оба собеседника получают одну и ту же строку независимо от
  того, кто вызывает), `format_safety_number()` (группировка по 5 цифр).
- `web_client.py`: `verified_peers.json` на аккаунт (не секрет — это лишь
  UI-пометка «сверено», как профили/webauthn-креды), привязана к хешу ИМЕННО
  того бандла пира, что был сверен (`mark_peer_verified`/`is_peer_verified`/
  `clear_peer_verified`) — если TOFU-пин пира сменится, хеш перестанет
  совпадать и пометка сама перестанет действовать, отдельный код
  инвалидации не нужен.
- `GET /api/safety-number/<peer>` / `POST /api/safety-number/<peer>/verify` —
  требуют полный бандл пира (X25519+Ed25519); легаси-пиры с 32-байтным
  бандлом без подписи получают явную ошибку «недоступно», а не тихий сбой.
- `static/app.js`: кнопка 🔒 в шапке DM-чата (`showSafetyNumber`) — модалка с
  числом, копированием и чекбоксом «сверено».
- `tests/test_safety_number.py` — симметричность, детерминированность,
  чувствительность к имени пользователя (не только к ключам), формат вывода,
  привязка пометки «сверено» к конкретному бандлу.

## Фаза 3 — Safety number (UI)

- Вычисление: детерминированная комбинация identity+signed prekey бандлов
  обеих сторон (в фиксированном порядке — например, отсортировать по имени
  пользователя, чтобы обе стороны считали одно и то же число) → SHA-256 →
  60 десятичных цифр, блоками по 5 (Signal-style).
- UI: в профиле контакта — кнопка «Проверить код безопасности», модалка с
  числом + QR-код (для сканирования при личной встрече).
- Не блокирует отправку сообщений (решение #7) — чисто информационный
  экран, доступный по желанию.
- Существующий механизм TOFU-алертов (`_pins`/`key_alerts`) не меняется —
  safety number дополняет его, не заменяет.

## Фаза 4 — Sender Keys для групп + leave/kick

- Каждый участник группы держит свою sender-ratchet-цепочку (аналог 1:1
  ratchet, но однонаправленную — только на отправку).
- Текущее состояние sender-цепочки рассылается остальным участникам через
  уже готовый парный Double Ratchet 1:1 (фаза 1) — то есть эта фаза целиком
  зависит от фазы 1 и не может начаться раньше неё.
- Новые операции: `POST /api/groups/<gid>/leave`, `POST
  /api/groups/<gid>/kick` (только для создателя/админа группы — нужно
  решить отдельно, кто имеет право кикать, если такого понятия сейчас нет
  вообще).
- При leave/kick: все ОСТАВШИЕСЯ участники обязаны сгенерировать НОВЫЙ
  sender key и разослать его друг другу заново — иначе ушедший участник
  продолжает расшифровывать будущие сообщения старым ключом. Это самая
  сложная по UX часть фазы (нужно решить, что происходит с недоставленными
  сообщениями старым ключом в момент ре-кея).
- Тесты: `tests/test_group_ratchet.py` — расширяет существующий
  `test_group_auth.py`; ключевой кейс — кикнутый участник математически не
  может расшифровать сообщение, отправленное ПОСЛЕ ре-кея, даже имея все
  свои старые ключи.

### Фаза 4 — РЕАЛИЗОВАНО

**Отклонение от исходного эскиза:** вместо полноценных Sender Keys
(однонаправленная sender-ratchet-цепочка на каждого участника) реализована
более простая, но решающая ту же задачу схема — общий симметричный групповой
ключ (как и был, без изменений в фазе 1) с ПОЛНОЙ ротацией при leave/kick,
разосланной остальным через уже существующий канал `ginvite`/`seal_group_key`
(а не через парный Double Ratchet 1:1, как предполагал эскиз — тот доступен
только между зарегистрированными аккаунтами с опубликованными prekeys,
`seal_group_key`+ECDH работает и для легаси/анонимных участников группы).
Дало то же самое свойство forward secrecy на leave/kick (ушедший не читает
НИЧЕГО после своего ухода — не только после N следующих сообщений своей
цепочки), ценой того, что каждый ре-кей — это новый ключ для ВСЕХ, а не
локальная ротация одной sender-цепочки. Для групп такого масштаба, для
которого спроектирован мессенджер, это разумный компромисс: полные Sender
Keys — отдельная, гораздо более крупная единица работы (нужен персистентный
per-sender ratchet-стейт на КАЖДОГО собеседника В КАЖДОЙ группе, аналог всей
фазы 2, но на N² комбинаций), не блокирующая forward secrecy как таковую.

**Право на kick:** сознательно НЕ ограничено создателем группы — та же
ungated-модель доверия, что уже была у `ginvite` (любой участник может
пригласить, значит любой может и исключить). Так проще (нет проблемы
«создатель ушёл — группу больше некому модерировать», нет отдельного
API переноса владения) и последовательно с уже принятым в проекте доверием
внутри группы. Самоисключение — только через `leave`, не через `kick` (сервер
явно отклоняет `kick(self)` с `ERR:use_leave`).

**Кто инициирует ре-кей:**
- **kick** — сам кикающий, синхронно в том же запросе (`kick_member` →
  `rekey_group`), поэтому результат детерминирован и мгновенен.
- **leave** (уходит сам, никто явно не решает «пора менять ключ») —
  децентрализованно: `check_group_rekey()` тикает в фоновом поллинге каждого
  клиента раз в 4 цикла, сравнивает текущий список участников с последним
  замеченным, и при усадке ре-кеит ТОЛЬКО тот участник, чьё имя
  лексикографически наименьшее среди оставшихся. Не таймер-дебаунс, как в
  референсе из репозитория друга (`memberLeftRotation.ts`) — детерминированный
  выборщик устраняет саму возможность гонки нескольких одновременных ре-кеев,
  а не гасит её постфактум.
- Доставка нового ключа и его подхват уже знающими группу участниками —
  через `fetch_groups()`, тоже вызываемый в фоновом поллинге; раньше эта
  функция игнорировала группы, ключ которых уже был известен клиенту
  (`if gid in self.group_keys: continue`) — пришлось заменить на сравнение с
  последним ПРИМЕНЁННЫМ блоком ключа (`_group_key_applied`), иначе ре-кей
  никогда бы не подхватывался уже состоящими в группе участниками.

**Новые примитивы протокола:** `CMD_GROUP_LEAVE`/`CMD_GROUP_KICK` (сигнатура
через уже существующий `_authorize_poll`, nonce+ts, та же модель — легаси/
анонимные имена проходят без проверки, как везде в проекте) и
`CMD_GROUP_MEMBERS` (список участников — не публичен, отдаётся только
проверенному действующему члену группы; без него ре-кею было бы некому
рассылать новый ключ).

**Реализовано:**
- `protocol.py`: `CMD_GROUP_LEAVE`/`CMD_GROUP_KICK`/`CMD_GROUP_MEMBERS`.
- `crypto_utils.py`: `gleave_signing_input`/`gkick_signing_input`/
  `gmembers_signing_input`.
- `server.py`: `_h_gleave`/`_h_gkick`/`_h_gmembers` — снимают участника из
  `grp['members']`+`grp['keys']`, отдают список участников только состоящему
  в группе.
- `web_client.py`: `UserMessenger.leave_group`/`kick_member`/
  `list_group_members`/`rekey_group`/`check_group_rekey`; `fetch_groups`
  переписан на отслеживание применённой версии ключа; фоновый поллинг
  (`start_poll_loop`) раз в 4 цикла гоняет `fetch_groups`+`check_group_rekey`;
  эндпоинты `/api/groups/leave`, `/api/groups/kick`, `/api/groups/members`.
- `static/app.js`: кнопка 👥 в шапке группового чата (`showGroupMembers`) —
  модалка со списком участников, кнопкой «Исключить» на каждом (кроме себя) и
  «Покинуть группу».
- `tests/test_group_rekey.py` — интеграционный тест через реальный
  `RelayServer`+`UserMessenger` (по образцу `test_group_auth.py`): kick
  синхронно ротирует ключ и рассылает его, кикнутый теряет доступ к группе и
  не может расшифровать пост-кик трафик старым ключом, подделанные kick/leave
  (чужое имя, мусорная подпись) отклоняются, децентрализованный ре-кей на
  добровольный leave срабатывает у детерминированно выбранного оставшегося
  участника и не срабатывает раньше времени на первом же наблюдении без
  базы для сравнения.

**Известное ограничение, не входящее в объём этой фазы:** обнаружен (не
здесь введён) реальный race condition в `transport.py` —
`UDPTransport.query()` делит один сокет между фоновым поллингом и
Flask-запросами того же пользователя без корреляции запрос/ответ, из-за чего
конкурентные вызовы могут получить чужой ответ. Заведена отдельная задача на
починку (не блокирует корректность самой фазы 4 — все ре-кей-тесты проходят
детерминированно в изолированном процессе без этой гонки).

## Порядок и зависимости фаз

```
Фаза 1 (X3DH + парный ratchet)
   │
   ├──> Фаза 2 (персистентность)
   │
   ├──> Фаза 3 (safety number) — независима от фазы 2, можно параллельно
   │
   └──> Фаза 4 (группы) — обязательно ПОСЛЕ фазы 1, использует её как транспорт
```

Рекомендуемый порядок реализации: 1 → 2 → 3 → 4. Фазы 2 и 3 можно поменять
местами или делать параллельно в разных сессиях без конфликта.

## Rollout

Жёсткое переключение (решение #4) — задеплоили новый `app.js`+`web_client.py`
одним деплоем через `deploy.sh`, без версионирования протокола. Сообщения,
оказавшиеся «в полёте» ровно в момент деплоя, в худшем случае теряются —
приемлемо для личного проекта. Каждая фаза деплоится и обкатывается отдельно
(это не один гигантский деплой на все 4 фазы разом).
